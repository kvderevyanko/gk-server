# Интеграция с Яндекс Умным домом (план)

Этот документ фиксирует целевую схему интеграции с Алисой. На момент его
создания интеграция не реализована: документ не описывает действующие
маршруты, реквизиты OAuth или развёрнутый публичный endpoint.

## Принцип подключения

Алиса и приложение «Дом с Алисой» взаимодействуют с облаком Яндекса. Облако
вызывает публичный HTTPS Adapter API провайдера, а не HTTP-сервер ESP и не
обычный пользовательский интерфейс приложения.

```text
Алиса / Дом с Алисой
          |
          v
    Облако Яндекса
          |
          | HTTPS, OAuth-токен пользователя
          v
  Отдельный Adapter API в Yii2
          |
          | внутренний вызов сценария
          v
  хранилище состояний и ESP transport
          |
          | HTTP в доверенной IoT-сети
          v
       ESP8266
          |
          v
    GPIO и нагрузка
```

Закрытая локальная сеть сама по себе не подходит как Endpoint URL: сервис
Яндекса должен суметь вызвать Adapter API. Для этого понадобится отдельный
публичный HTTPS-вход, например reverse proxy на защищённом шлюзе с туннелем
до локальной сети. Публичный вход предоставляет только маршруты интеграции;
web UI, SQLite и ESP не публикуются.

## Протокол Яндекса

Планируется REST-вариант Provider API:

| Метод и путь | Назначение в приложении |
|---|---|
| `HEAD /v1.0/` | проверка доступности endpoint |
| `GET /v1.0/user/devices` | вернуть виртуальные устройства, доступные пользователю |
| `POST /v1.0/user/devices/query` | вернуть известное состояние устройств |
| `POST /v1.0/user/devices/action` | преобразовать голосовую команду в сценарий |
| `POST /v1.0/user/unlink` | отозвать привязку аккаунта |

Для привязки аккаунта потребуется OAuth 2.0: Adapter API проверяет токен
пользователя из запроса Яндекса и определяет, какие виртуальные устройства ему
доступны. В запросах и логах сохраняется `X-Request-Id`, чтобы сопоставлять
команду Алисы с её результатом.

Официальные контракты: [протокол Provider API](https://yandex.ru/dev/dialogs/smart-home/doc/ru/reference/resources), [авторизация](https://yandex.ru/dev/dialogs/smart-home/doc/ru/auth/how-it-works), [изменение состояния](https://yandex.ru/dev/dialogs/smart-home/doc/ru/reference/post-action).

## Сценарии и виртуальные устройства

Первый этап ограничен GPIO. Оператор создаёт сценарий с понятным именем и
упорядоченными шагами вида:

```text
ESP-устройство + номер GPIO + значение 0 или 1
```

Затем он создаёт виртуальный выключатель, например «Свет на балконе», и
привязывает к нему два сценария: один для `on`, второй для `off`.

Яндекс передаёт действие над внешним идентификатором виртуального устройства,
а не внутренний идентификатор сценария. Yii2 по своей привязке определяет,
какой сценарий выполнить. Поэтому внутренние первичные ключи не попадают в
контракт с внешней платформой.

При выполнении сценария сервис обязан сначала валидировать все шаги, затем
обновить целевые GPIO-состояния и сгруппировать отправку по ESP. Для одного
ESP отправляется один полный GPIO-запрос, а не последовательность одиночных
переключений. Это сохраняет согласованность существующей модели GPIO и
уменьшает промежуточные физические состояния.

## Результат и состояние

Успех (`DONE`) возвращается только после подтверждения команды ESP. Результат
каждого шага/устройства сохраняется в журнале доставки вместе с идентификатором
запроса Яндекса.

Текущий протокол ESP подтверждает принятие GPIO-команды, но не измеряет
фактическое состояние подключённой нагрузки. Поэтому до добавления физической
обратной связи статус в Алисе означает «команда принята контроллером», а не
измеренное состояние света или реле.

## Границы первого этапа

В первую реализацию не входят PWM, WS2812, DHT, датчики, расписания и
произвольные автоматизации. Их модель и сопоставление с возможностями Яндекса
определяются отдельной задачей после проверки GPIO-сценариев на живом
оборудовании.
