# Разработка

## Требования из репозитория

`composer.json` требует:

- PHP `^7.4 || ^8.1`;
- Yii2 `~2.0.14`;
- расширения и пакеты для SQLite, HTTP-клиента, Bootstrap, SwiftMailer и Chart.js;
- Codeception 4 и модули тестирования в `require-dev`.

Рабочий экземпляр проверен на PHP 8.1. Поддержка PHP 7.4 сохранена для
совместимости, но эта ветка PHP больше не получает исправления безопасности и
не рекомендуется для нового production-развёртывания.

## Состояние рабочей копии

На момент составления документации отсутствуют:

- каталог `vendor/`;
- файл `db/sqlite.db`.

Следствия:

- приложение не запустится до установки Composer-зависимостей;
- `composer install` использует зафиксированные версии из `composer.lock`;
- совместимость зависимостей с целевой версией PHP должна проверяться в
  подготовленном окружении;
- миграции нельзя выполнить до появления `vendor/`.

## Подготовка

Из корня `gk-server`:

```bash
composer install
php yii app/start
php yii migrate
```

Это команды, соответствующие текущей структуре проекта, но в исходном состоянии репозитория их успешное выполнение не подтверждено.

Особенности `app/start`:

- выставляет `0775` для `runtime`, `web/assets` и `db`;
- создаёт `db/sqlite.db`, если файла нет;
- выставляет файлу БД `0664`;
- напоминает назначить владельца/группу веб-процесса;
- отсылает к актуальной документации cron.

Запись должна быть доступна только владельцу и группе веб-процесса. Для
совместной работы пользователя развёртывания и PHP удобно использовать общую
группу и setgid-бит на writable-каталогах.

## Запуск веб-приложения

Document root должен указывать на `gk-server/web`. Для быстрого локального запуска после установки зависимостей можно использовать встроенный сервер PHP:

```bash
php yii serve --port=8080
```

Либо настроить Apache/Nginx так, чтобы несуществующие файлы перенаправлялись в `web/index.php`. Pretty URL включены, `showScriptName` выключен.

### Локальный Docker

Для повторяемого локального запуска в корне есть `Makefile`. Перед первым
запуском создайте игнорируемый `.env` по образцу `.env.example` с уникальным
`COOKIE_VALIDATION_KEY`, затем выполните:

```bash
make init
make dev-up
```

Интерфейс будет доступен на `http://127.0.0.1:8080/`, если `HTTP_PORT` не
переопределён в `.env`. `make init` также назначает владельцем persistent-
каталогов пользователя `www-data` внутри контейнера. `make dev-up` запускает
web-интерфейс с read-only mounts исходного кода; после этого изменения PHP,
views, CSS и JS видны без rebuild или перезапуска контейнера. Может
потребоваться обычное обновление страницы или hard reload для browser cache.

`make up` запускает web-интерфейс из собранного образа; он безопасен для
локальной проверки, потому что scheduler не выполняет фоновые команды ESP.
Повторная сборка нужна только при изменении зависимостей, Dockerfile или Docker/
Compose-конфигурации.
Для полного контура есть явная команда `make up-all`. Доступны также `make ps`,
`make logs`, `make lint` и `make down`.

SQLite-файл и каталоги `runtime`, `web/assets` должны быть доступны на запись процессу PHP.

## Конфигурация

Точки входа web и console по умолчанию запускаются с `YII_ENV=prod` и
`YII_DEBUG=false`. Для локальной разработки dev-режим включается явно:

```bash
export COOKIE_VALIDATION_KEY="$(php -r 'echo bin2hex(random_bytes(32));')"
YII_ENV=dev YII_DEBUG=1 php yii
```

`COOKIE_VALIDATION_KEY` обязателен и не хранится в Git. Его задают в окружении
веб-сервера и консольных процессов либо в игнорируемом `.env` (если окружение
развёртывания загружает такой файл). Для каждого окружения следует создать своё
случайное значение; шаблон приведён в `.env.example`.

Остальная конфигурация пока не полностью вынесена в переменные окружения:

- DSN задан непосредственно в `config/db.php`;
- production и development используют общую конфигурацию приложения.

При локальной работе не следует коммитить реальные сетевые адреса устройств, секреты Wi-Fi или рабочую БД. `db/.gitignore` исключает содержимое каталога БД.

## Проверки

### Синтаксис PHP

Проверка не требует `vendor/`:

```bash
find . -name '*.php' -not -path './vendor/*' -print0 \
  | xargs -0 -n1 php -l
```

Она проверяет только синтаксис и не доказывает совместимость с версией Yii2 или корректность выполнения.

### Codeception

После установки dev-зависимостей:

```bash
vendor/bin/codecept run
```

Фактическое покрытие минимально:

- есть один acceptance-тест `tests/acceptance/FirstCest.php`;
- он открывает `/` по адресу `http://gk-server/`;
- проверяется только наличие текста `Главная`;
- содержательных unit- и functional-тестов нет.

Перед acceptance-тестом нужен доступный виртуальный хост `gk-server` либо изменение локальной конфигурации `tests/acceptance.suite.yml`.

### Проверка миграций

После установки зависимостей и создания БД:

```bash
php yii migrate/history
php yii migrate
```

Для проверки с чистой БД следует использовать отдельный временный SQLite-файл через отдельную конфигурацию. Репозиторий содержит `config/test_db.php`, но штатная консольная конфигурация использует `config/db.php`.

### Проверка NodeMCU Lua

Прошивки ESP8266 используют Lua 5.1-совместимый NodeMCU. Для воспроизводимой
синтаксической проверки в репозитории есть проектный bootstrap: он скачивает
проверенный исходный архив Lua 5.1.5 и собирает инструменты только в
игнорируемом каталоге `.tools/`; системные пакеты и ESP-устройства не меняются.

```bash
tools/bootstrap-lua51.sh
tools/check-nodemcu-lua.sh
```

`check-nodemcu-lua.sh` проверяет все `nodemcu/**/*.lua` через Lua 5.1. Для
готового совместимого компилятора можно задать `LUA51_LUAC=/path/to/luac`.
Эта проверка не эмулирует модули NodeMCU и не подтверждает работу с реальным
оборудованием.

Небольшая проверка логики GPIO/PWM/WS на моках запускается тем же Lua 5.1:

```bash
.tools/lua-5.1.5/bin/lua tests/nodemcu/smoke.lua
.tools/lua-5.1.5/bin/lua tests/nodemcu/server_smoke.lua
```

Она проверяет повторные GPIO-команды, повреждённый файл состояния, конфликт
пинов и то, что выключение WS не запускает тестовый PWM-индикатор на D4.
Отдельный HTTP-мок проверяет частичный запрос, токен, ошибку обработчика,
ограничение длины и передачу статического файла без обрезания.

### Инструменты для ESP8266

Инструменты для чтения и прошивки ESP8266 также устанавливаются локально в
`.tools/`, а их версии закреплены в `tools/nodemcu-tools-requirements.txt`:

```bash
tools/bootstrap-nodemcu-tools.sh
tools/probe-esp8266.sh /dev/ttyUSB0
```

`probe-esp8266.sh` выполняет только `chip_id` и `flash_id`: он сбрасывает
контроллер в bootloader для связи, но не записывает и не стирает flash.
Запись прошивки и управляющие запросы к GPIO/PWM требуют отдельного явного
подтверждения, потому что могут изменить состояние подключённой периферии.

Перед заменой прошивки устройства с 4 MiB flash нужно сохранить полный образ
в локальном игнорируемом каталоге `.local/esp-backups/`:

```bash
tools/backup-esp8266.sh /dev/ttyUSB0
```

По умолчанию чтение идёт на консервативной скорости 115200 baud, а подробный
вывод `esptool` и SHA-256 образа остаются рядом с backup только в `.local/`.
Если конкретный USB-UART стабильно работает быстрее, скорость можно повысить,
например `ESPTOOL_BAUD=460800 tools/backup-esp8266.sh /dev/ttyUSB0`.

Для общего варианта `nodemcu/code` проект содержит последовательность записи
прошивки и файлов. Скрипт развёртывания очищает файловую систему ESP, а потому
перед ним обязателен backup. Скопируйте
`nodemcu/code/_config.example.lua` в `.local/nodemcu/_config.lua`, настройте
Wi-Fi и передайте этот отдельный локальный файл скрипту; SSID и пароль в Git
не попадают.

```bash
tools/flash-nodemcu.sh /dev/ttyUSB0
tools/deploy-nodemcu-code.sh /dev/ttyUSB0 .local/nodemcu/_config.lua
```

Для чтения вывода UART без отправки Lua-команд используется project-local
монитор:

```bash
.tools/nodemcu-python/bin/python tools/read-esp-serial.py /dev/ttyUSB0 --baud 115200
```

## Ограничения локальной проверки

Без реального ESP можно проверить веб-CRUD и работу SQLite, но действия GPIO/PWM/DHT/WS будут обращаться к адресу из `device.host` и ждать до двух секунд. Встроенного эмулятора ESP или мок-транспорта в репозитории нет.
