# Технические риски и приоритеты

Приоритеты ниже основаны на влиянии на безопасность, воспроизводимость и эксплуатацию текущего кода.

## P0 — устранить до публикации в недоверенной сети

### Нет аутентификации и авторизации

В контроллерах отсутствует `AccessControl`; модель пользователя, указанная в конфигурации, не образует видимого защитного контура для действий управления. Доступный по сети пользователь может менять конфигурацию и физическое состояние GPIO/PWM/WS.

Необходимо закрыть приложение сетевым уровнем либо реализовать вход, роли и проверку доступа на всех управляющих маршрутах.

### Изменение состояния через GET

`pwm/request/set` и `ws/ws/request` меняют БД и оборудование через GET. Это допускает случайные повторные запросы, prefetch и CSRF-сценарии. GPIO уже переведён на `POST` с CSRF и `VerbFilter`.

Необходимо перевести оставшиеся изменяющие действия на POST/PUT, оставить CSRF-защиту включённой и явно ограничить методы через `VerbFilter`.

### Секрет в репозитории и слабая конфигурация ESP

Cookie validation key зафиксирован в `config/web.php`. Стандартный пароль точки доступа ESP равен предсказуемому `ESP-<chipid>`. HTTP между сервером и ESP не имеет шифрования или аутентификации.

Необходимо вынести секреты из репозитория, сменить ключи и ограничить ESP изолированной доверенной сетью. Для команд к ESP требуется как минимум сетевой ACL; предпочтительно добавить проверяемую авторизацию протокола.

## P1 — высокий риск эксплуатации и развёртывания

### Устаревающая платформа PHP

`composer.json` допускает PHP 7.4 и 8.1, а рабочий экземпляр проверен на PHP
8.1. Обе ветки требуют запланированного обновления до поддерживаемой версии
PHP вместе с Yii2 и зависимостями; одного изменения Composer constraint для
этого недостаточно.

### Ошибки подавляются

Пустые `catch` присутствуют при отправке GPIO из cron, работе motor cron и обработке ответа DHT. Оператор не получает причину отказа, а система может считать состояние применённым, хотя ESP недоступен.

Необходимо журналировать устройство, endpoint, исключение и результат сохранения. Для управления оборудованием полезно хранить отдельно желаемое и подтверждённое состояние.

### Состояние БД не гарантирует состояние оборудования

GPIO/PWM/WS сначала сохраняются в SQLite, затем отправляются на ESP. При сетевой ошибке БД уже содержит новое значение. Повторная синхронизация реализована только через следующую ручную операцию или cron для отдельных функций.

Нужны статус доставки, повторные попытки с ограничением и команда полной синхронизации устройства.

## P2 — целостность данных и функциональные пробелы

### Нет ограничений целостности

Большинство таблиц не имеет внешних ключей и уникальных индексов. Возможны:

- периферия несуществующего устройства;
- несколько записей одного пина;
- несколько `pwm_settings` или `ws_values` для устройства;
- дубли ключей `settings`;
- история без родительского устройства.

Нужно определить кардинальности, очистить существующие данные и добавить внешние ключи/уникальные индексы. Для SQLite следует явно включить и проверить поддержку foreign keys.

### PWM-расписания не реализованы

`CommandsPwmSetSettings::set()` пуст, а `CommandController` обрабатывает только GPIO. Интерфейс и подписи моделей создают впечатление поддержки PWM, которой фактически нет.

Либо реализовать и протестировать PWM-ветку, либо убрать её из интерфейса и документации продукта.

### Расписания ограничены текущим часом

Условия используют только целый час `date('H')`, не учитывают минуты, дни недели и интервалы через полночь. Часовой пояс приложения не задан явно.

Нужно формализовать модель расписаний и зафиксировать timezone.

### Логика motor зависит от частоты cron

Команда переключает значение на основании номера минуты и текущего состояния. Пропуск или повторный запуск меняет фактическую длительность импульса. Комментарий о включении на 20 секунд не соответствует реализации.

Нужно заменить переключение явным конечным автоматом/задачей с временем следующего действия.

### Неоднозначность протокола PWM

Сервер передаёт `duty`, но Lua-обработчик использует значения пинов и игнорирует отдельный параметр `duty`. Нет общей схемы или версии протокола.

Нужно зафиксировать контракт endpoint-ов и добавить интеграционные тесты против эмулятора ESP.

## P3 — сопровождаемость

### Почти отсутствуют тесты

Есть один acceptance-тест главной страницы; unit- и functional-сценариев нет. Не проверяются миграции, модели, расписания, преобразование цветов и протокол ESP.

Минимальный набор:

1. unit-тесты преобразований и расчёта расписаний;
2. тесты Active Record на временной SQLite;
3. тест HTTP-транспорта с локальным fake ESP;
4. smoke-тест миграций с пустой БД;
5. сценарии ошибок и тайм-аутов.

### Дублированные варианты NodeMCU-кода

Общий код и каталоги `custom/enik`, `custom/robat` содержат похожие файлы и минифицированные копии. Не определено, что является каноническим исходником и как воспроизводятся бинарные прошивки.

Нужно выделить общий код, конфигурации устройств и воспроизводимый процесс сборки/загрузки.

### Бинарные артефакты хранятся вместе с исходниками

В репозитории находятся `.bin`, ZIP ESPlorer, изображения и минифицированные ресурсы. Это увеличивает репозиторий и затрудняет аудит происхождения сборок.

Следует документировать происхождение и версии либо перенести релизные артефакты в отдельное хранилище.

### Устаревшая эксплуатационная документация

`docs/system/system.md` содержит маршруты консольных команд, которых больше нет, и небезопасные инструкции с `chmod 777`.

Новая документация в `docs/project/` отражает текущий код, но старые инструкции следует либо обновить, либо явно пометить архивными после согласования.
