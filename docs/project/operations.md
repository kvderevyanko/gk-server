# Эксплуатация

## База данных и миграции

Приложение использует SQLite-файл:

```text
db/sqlite.db
```

Создание файла предусмотрено командой:

```bash
php yii app/start
```

Применение схемы:

```bash
php yii migrate
```

Просмотр состояния:

```bash
php yii migrate/history
php yii migrate/new
```

Перед миграциями в рабочей среде следует остановить задания, которые пишут в БД, и сделать копию `db/sqlite.db`. В репозитории нет отдельного механизма резервного копирования.

Для добавления журнала доставки команд применяется миграция
`m260913_000000_create_command_delivery_table`. Она только создаёт новую таблицу
и индексы; перед её применением всё равно нужна копия рабочей SQLite. После
миграции страница устройства показывает последние результаты доставки GPIO,
PWM, DHT и WS2812.

Миграции создают таблицы устройств, периферии, истории DHT, расписаний и настроек. Для SQLite внешние ключи фактически не добавляются, поэтому приложение удаляет связанные данные вручную в одной транзакции при удалении устройства: GPIO, PWM, WS2812, DHT, историю температур, расписания, настройки устройства и журнал доставки команд. Удаление необратимо и не меняет данные или прошивку на физическом ESP.

## Docker-развёртывание

`compose.yaml` запускает два контейнера из одного образа PHP 8.1: `web` с
Apache и `scheduler` с Yii-задачами. Веб-контейнер по умолчанию слушает только
`127.0.0.1:8080`. При наличии нескольких сайтов, TLS или внешнего WAF к нему
подключают Apache/nginx через reverse proxy. Для единственного локального
сервиса можно слушать сразу LAN-адрес хоста: в игнорируемом `.env` указывают
`HTTP_BIND_ADDRESS` и `HTTP_PORT=80`, после чего хостовый веб-сервер не нужен.
Не публикуйте контейнер на `0.0.0.0`, если доступ к приложению нужен только из
локальной сети.

Состояние не находится внутри образа: каталоги `db/`, `runtime/` и
`web/assets/` примонтированы с хоста. Перед первым запуском действующей
системы обязательно сделать и проверить резервную копию `db/sqlite.db`.
Для staging-развёртывания их абсолютные пути можно задать в `.env` через
`DB_DIR`, `RUNTIME_DIR` и `ASSETS_DIR`.

При сборке Docker образа исходники могут иметь на хосте строгие права, например
`0600`. Dockerfile нормализует права копии внутри образа до читаемых веб-процессом;
права файлов на хосте при этом не меняются. Секретные `.env` и `.local` исключены
из build context.

В корне проекта создают игнорируемый `.env` с уникальным значением:

```dotenv
COOKIE_VALIDATION_KEY=replace-with-a-random-32-byte-secret
```

Запуск и проверка:

```bash
docker compose build
docker compose run --rm web php yii migrate --interactive=0
docker compose up -d
docker compose ps
curl --fail http://127.0.0.1:8080/
```

Для локальной разработки те же действия, включая корректные права persistent-
каталогов для `www-data`, собраны в `make init`; web-интерфейс без scheduler
запускается через `make up`.

Не запускайте одновременно старый cron хоста и контейнер `scheduler`: иначе
команды к ESP и опрос DHT будут дублироваться. Переключение reverse proxy и
отключение старого cron выполняют только после успешной проверки контейнера.

## Периодические задания

Фактические консольные маршруты:

| Команда | Назначение | Рекомендуемая базовая частота |
|---|---|---|
| `php yii command/index` | применить почасовые правила GPIO | раз в минуту |
| `php yii dht/index` | опросить все активные DHT | по нужной частоте, например раз в 10 минут |
| `php yii motor/motor` | обновить GPIO с флагом `motor` | раз в минуту |

Yii допускает сокращение `command/index` до `command` и `dht/index` до `dht`.

Пример crontab:

```cron
* * * * * cd /absolute/path/to/gk-server && /usr/bin/php yii command/index >> runtime/cron-command.log 2>&1
*/10 * * * * cd /absolute/path/to/gk-server && /usr/bin/php yii dht/index >> runtime/cron-dht.log 2>&1
* * * * * cd /absolute/path/to/gk-server && /usr/bin/php yii motor/motor >> runtime/cron-motor.log 2>&1
```

Пути к проекту и PHP должны быть абсолютными. Запускающий пользователь должен иметь запись в `runtime/` и `db/sqlite.db` и сетевой доступ к ESP.

Старая инструкция `docs/system/system.md` содержит команды `device/temperature` и `device/motor`. Таких действий в текущем `DeviceController` нет; для текущего кода нужны маршруты из таблицы выше.

### Поведение расписаний

`command/index`:

- выбирает только активные команды активных устройств;
- сортирует их по `conditionSort`;
- группирует по типу, устройству и пину;
- обрабатывает только `pinType=gpio`;
- сравнивает текущий час сервера с интервалом `[conditionFrom, conditionTo)`;
- сохраняет выбранное значение и отправляет весь набор GPIO устройства на ESP.

Правила через полночь отдельной логикой не поддержаны. Часовой пояс берётся из окружения PHP/ОС; приложение явно его не задаёт.

`motor/motor` использует номер текущей минуты и настройку `MOTOR_INTERVAL`. При кратной интервалу минуте выключенный motor GPIO включается, в остальные вызовы либо при уже включённом значении — выключается. Это не таймер точной длительности.

## Подготовка ESP8266 / NodeMCU

В репозитории находятся:

- бинарные прошивки в `nodemcu/firmware/`;
- архив ESPlorer;
- общий Lua-код в `nodemcu/code/`;
- варианты `nodemcu/custom/enik` и `nodemcu/custom/robat`.

Для общего варианта `nodemcu/code/` процесс прошивки и загрузки файлов автоматизирован скриптами в `tools/`. Перед работой необходимо выбрать бинарную прошивку с модулями, используемыми конкретной конфигурацией. Общий код зависит как минимум от `file`, `gpio`, `net`, `node`, `pwm`, `sjson`, `tmr`, `uart`, `wifi`, `dht`, `pixbuf`, `ws2812` и вспомогательных цветовых модулей для светодиодных эффектов.

Базовая последовательность:

1. Запустить `tools/bootstrap-nodemcu-tools.sh` и проверить чип через `tools/probe-esp8266.sh`.
2. Сохранить полный образ flash в `.local/esp-backups/` командой `tools/backup-esp8266.sh`.
3. Создать локальный `.local/nodemcu/_config.lua` с режимом Wi-Fi и реквизитами сети; этот файл не коммитится.
4. Прошить подходящий `.bin` через `tools/flash-nodemcu.sh`.
5. Загрузить общий код и локальную конфигурацию через `tools/deploy-nodemcu-code.sh`.
6. Убедиться по UART, что Lua-файлы скомпилированы, Wi-Fi подключён и сервер запущен.
7. Записать в `device.host` полный HTTP-префикс контроллера с завершающим `/`.

`compile.lua` компилирует перечисленные `.lua` в `.lc` и удаляет загруженные исходники на ESP. Сервер затем вызывает именно `.lc`. Конфигурация остаётся локальным файлом `_config.lua` и компилируется в `_config.lc`.

Для включённого в репозиторий образа скрипт использует режим flash `dio`,
который указан в заголовке образа. Только для платы с иной подтверждённой
распайкой его можно изменить через `ESP_FLASH_MODE` (`qio`, `qout` или
`dout`).

Шаблон `nodemcu/code/_config.example.lua` поднимает точку доступа:

```text
SSID: ESP-<chipid>
пароль: ESP-<chipid>
IP: 192.168.111.1
порт: 80
```

Скопируйте шаблон в `.local/nodemcu/_config.lua` и задайте собственные
параметры до загрузки. Значения шаблона пригодны для первичной настройки, но
пароль предсказуем и не подходит для доверенной рабочей сети.

Для постоянного адреса в Station или Station+AP задайте в локальной
конфигурации `conf.wifi.station.ip`, `netmask` и `gateway`. Адрес следует
сначала исключить из DHCP-пула или зарезервировать на роутере по MAC ESP.

## Быстрая диагностика

### Сервер не запускается

Проверить:

```bash
test -f vendor/autoload.php
php -v
php yii help
ls -l db db/sqlite.db runtime web/assets
```

Если `vendor/autoload.php` отсутствует, зависимости не установлены. Если `db/sqlite.db` отсутствует, выполнить `php yii app/start`, затем миграции.

### Ошибка SQLite

Проверить наличие расширения и доступ:

```bash
php -m | grep -i sqlite
sqlite3 db/sqlite.db '.tables'
```

Процесс веб-сервера и пользователь cron должны иметь права на запись в файл БД и каталог `db/`.

Для Apache `mpm_event` или nginx PHP следует запускать через PHP-FPM. При
небольшой локальной нагрузке замена Apache `mpm_event + PHP-FPM` на nginx сама
по себе не даёт существенного выигрыша. Выбор nginx имеет смысл при появлении
отдельных требований к reverse proxy, TLS или большому числу одновременных
соединений.

### ESP не отвечает

Проверить адрес устройства и обработчики напрямую:

```bash
curl --max-time 2 'http://ESP_HOST/gpio.lc?1=0'
curl --max-time 2 'http://ESP_HOST/dht.lc?pin=1'
```

GPIO-команда меняет физическое состояние и должна использоваться только с безопасным тестовым пином. Сервер Yii2 использует такой же двухсекундный тайм-аут.

На ESP проверить через UART:

- получение IP;
- сообщение о запуске сервера;
- наличие нужных `.lc`;
- ошибки памяти и перезапуски watchdog;
- наличие каталога `json` и файлов состояния.

### DHT не сохраняет историю

Проверить:

- активны ли и устройство, и запись DHT;
- совпадает ли пин;
- возвращает ли `dht.lc` JSON со `status: ok`;
- существует ли поле `pin` в `temperature_info`, то есть применена ли миграция `m230923_064503`;
- появляются ли строки после ручного `php yii dht/index`.

Текущий код подавляет ошибки декодирования и сохранения, поэтому отсутствие строки в БД может не сопровождаться сообщением.

### Cron не управляет GPIO

Проверить:

- тот ли PHP используется в cron;
- рабочий каталог и абсолютный путь к `yii`;
- часовой пояс процесса;
- активность `commands`, `device` и `gpio`;
- `pinType` должен быть `gpio`;
- текущий час должен попадать в `[conditionFrom, conditionTo)`;
- доступ к ESP из-под пользователя cron.

Для диагностики обязательно перенаправлять stdout/stderr в отдельные файлы, как в примере crontab.

## Журналы

Yii пишет уровни `error` и `warning` через `FileTarget`, обычно в `runtime/logs/app.log`. Не все операционные ошибки туда попадают: несколько `catch` оставлены пустыми. Поэтому при проблемах нужны одновременно:

- журнал Yii;
- вывод cron;
- access/error log веб-сервера;
- UART-вывод ESP;
- прямой HTTP-запрос к ESP.
