# Архитектура и потоки данных

## Общая схема

```text
Браузер
   |
   | HTTP к Yii2
   v
Веб-приложение gk-server
   |                    |
   | Active Record      | HTTP GET, timeout 2 с
   v                    v
SQLite               ESP8266 / NodeMCU
db/sqlite.db          Lua HTTP-сервер, порт 80
                         |
                         v
                 GPIO / PWM / DHT / WS2812
```

Yii2 является источником конфигурации и желаемого состояния. Для GPIO, PWM и WS2812 изменение сначала сохраняется в SQLite, после чего сервер формирует полный набор актуальных параметров устройства и отправляет его на ESP. Для DHT направление данных обратное: Yii2 запрашивает показания у ESP и сохраняет успешный ответ в таблице истории.

## Серверная часть

Проект основан на Yii2 Basic Project Template:

- `web/index.php` создаёт веб-приложение из `config/web.php`;
- `yii` создаёт консольное приложение из `config/console.php`;
- `config/db.php` задаёт SQLite DSN `sqlite:@app/db/sqlite.db`;
- модели используют Yii Active Record;
- модули `gpio`, `pwm`, `dht`, `ws`, `ssd1306` и `gamepad` подключены в `config/web.php`.

`web/index.php` и `yii` по умолчанию используют production-режим. Для
локальной разработки `YII_ENV=dev` и `YII_DEBUG=1` задаются явно через
окружение.

## Модель устройств

Центральная таблица `device` содержит имя, HTTP-адрес `host`, признаки активности и отображения, тип и иконку. Поддерживаемым типом в `Device::typeList()` фактически выставлен только `ESP8266`; константа ESP32 существует, но в список выбора не включена.

Периферийные записи связываются с устройством полем `deviceId`:

| Таблица | Содержимое |
|---|---|
| `gpio` | пин, логическое значение, инверсия, признаки активности/мотора |
| `pwm_values` | пин и значение PWM |
| `pwm_settings` | частота `clock` и `duty` устройства |
| `dht` | пин датчика DHT |
| `temperature_info` | история температуры и влажности по устройству и пину |
| `ws_values` | режим и параметры WS2812 |
| `commands` | интервалы времени и значения пинов |
| `command_delivery` | журнал попыток доставки команд и подтверждений ESP |
| `settings` | общие параметры приложения |
| `device_settings` | включённые для устройства типы возможностей |
| `ssd1306_images` | данные изображений SSD1306 |

Миграции почти не создают внешних ключей. Единственная попытка добавить внешний ключ находится в миграции `device_settings`, но для SQLite она намеренно пропускается.

## Запросы к ESP

Фабрика `EspRequestSenderFactory` создаёт один из двух клиентов:

- `EspCurlRequest` — выбран по умолчанию;
- `EspHttpRequest` — stream transport.

Оба выполняют HTTP GET с тайм-аутом 5 секунд. Это оставляет конечную границу
для недоступного устройства и позволяет ESP8266 завершить восстановление
состояния сразу после перезапуска. Адрес собирается простой конкатенацией
`device.host` и имени файла, поэтому значение `host` должно уже иметь корректный
завершающий `/`, например `http://192.168.1.50/`.

Используемые обработчики ESP:

| Возможность | Путь на ESP | Параметры |
|---|---|---|
| GPIO | `gpio.lc` | пары `пин=0/1` |
| PWM | `gpio-pwm.lc` | пары `пин=значение`, `clock`, `duty` |
| DHT | `dht.lc` | `pin` |
| WS2812 | `ws.lc` | `buffer`, `mode`, `delay`, `bright`, цвета и опции |

Каждый обработчик команд возвращает JSON с `status` и понятным `message`.
Для GPIO и PWM успешный ответ также содержит принятые пины; для WS2812 —
применённые параметры; DHT добавляет номер пина и показания. Некорректный
запрос не меняет сохранённое состояние и получает `status="error"` с объектом
`rejected` либо сообщением о неверном параметре.

HTTP-статус, отличный от успешного, преобразуется в строку `error`. Сетевые исключения в части cron-кода подавляются без журналирования.

## Журнал доставки команд

Таблица `command_delivery` хранит неизменяемую запись каждой попытки из
интерактивных GPIO, PWM, DHT и WS2812-контроллеров: тип, устройство, при
наличии пин, итог (`confirmed` или `error`), сообщение, полезную нагрузку и
время. Эта запись не заменяет желаемое состояние в таблицах периферии и не
является измерением физического уровня на выводе: `confirmed` означает только,
что ESP ответил успехом на конкретную команду.

Журнал намеренно не влияет на доставку: ошибка записи истории лишь попадает в
Yii log и не меняет уже полученный результат команды. На странице устройства
показываются восемь последних попыток; обзор читает до шести последних записей
для избранных устройств. Оба экрана читают только SQLite и не вызывают ESP.

## Поток GPIO

1. Браузер вызывает `gpio/request/set` методом `POST` с CSRF-токеном, `deviceId`, `pin` и `value`.
2. `Gpio::setStatus()` сохраняет значение активной записи.
3. `Gpio::sendRequest()` выбирает все активные GPIO активного устройства.
4. Для пинов с `negative=true` значение инвертируется.
5. Сервер отправляет все пины на `<host>gpio.lc`.
6. Lua проверяет, что каждый пин находится в диапазоне `0…9`, а значение равно
   `0` или `1`; при любой ошибке весь запрос отклоняется.
7. При успехе Lua выставляет режим `gpio.OUTPUT` только при первом назначении
   пина GPIO после запуска. Повтор того же уровня не вызывает `gpio.mode()` и
   `gpio.write()`. Командное состояние сохраняется в `json/gpio-action.json`;
   восстановление из файла не перезаписывает его.
8. Ответ имеет вид `{"status":"ok","message":"GPIO command accepted","pins":{"4":0}}`.
   Поле `pins` отражает принятые команды, а не измеренное физическое состояние
   вывода. Отклонённый запрос возвращает `status="error"` и объект `rejected`
   с причинами по пинам.

Контроллер принимает только `POST` и строго читает `deviceId`, `pin` и `value`
из POST body; успешный ответ — JSON с `status="ok"`.
При ошибке доставки он возвращает HTTP 502 и JSON со `status="error"`: значение
уже сохранено как желаемое, но пользователь явно видит, что ESP его не подтвердил.
Результат каждой попытки записывается в `command_delivery`.

## Поток PWM

1. Браузер вызывает `pwm/request/set` методом `POST` с CSRF-токеном, `deviceId`, `pin` и `value` (`0…1023`).
2. Значение сохраняется в `pwm_values`.
3. `Pwm::sendRequest()` загружает все активные PWM-пины и единственную запись `pwm_settings` устройства.
4. Параметры отправляются на `<host>gpio-pwm.lc`.
5. Lua вызывает `pwm.setup()` и `pwm.start()`, затем сохраняет состояние в `json/pwm-action.json`.

PWM принимает только целую частоту `1…1000`, номера пинов `1…9` и duty
`0…1023` (не более шести пинов). D0 не поддерживает PWM. При ошибке хотя бы
одного значения команда не применяется частично.
Исторический параметр `duty` из `pwm_settings` не является пином и сохраняется
на сервере только для обратной совместимости: ESP использует duty конкретных
пинов.

Параметр `duty` передаётся сервером, но текущий `gpio-pwm.lua` его отдельно не обрабатывает: значениями duty служат значения конкретных пинов.

Контроллер строго читает параметры из POST body и отвечает JSON. Ошибка доставки
возвращает HTTP 502: сохранённое значение остаётся желаемым, но не считается
подтверждённым ESP.
Результат каждой попытки записывается в `command_delivery`.

## Поток DHT

1. Браузер вызывает `dht/request/get-temperature` методом `POST` с CSRF-токеном, `deviceId` и `pin`; периодический опрос запускается командой `php yii dht/index`.
2. `Dht::sendRequest()` проверяет активность датчика и устройства.
3. Yii2 запрашивает `<host>dht.lc?pin=...`.
4. Lua принимает пины `1…9`, вызывает `dht.read()` и возвращает JSON; D0 для
   DHT не поддерживается.
5. При `status=ok` сервер сохраняет температуру, влажность, `deviceId`, `pin` и Unix timestamp в `temperature_info`.
6. Успешный HTTP-ответ браузеру — JSON с `status=ok` и полученными значениями; ошибка доставки или неподтверждённый ответ возвращаются как JSON с `status=error` и HTTP 502.
7. `dht/request/get-graph-info` остаётся read-only GET и отдаёт последние 100 записей для графика.

Интерфейс не повторяет опрос автоматически: оператор сам решает, нужно ли повторить запрос к датчику.
Результат ручного опроса также записывается в `command_delivery`; периодический
console-опрос в этот журнал не пишется.

## Поток WS2812

Браузер вызывает `ws/ws/request` только методом `POST` с CSRF-токеном и полным
набором параметров текущей карточки: `deviceId`, `buffer`, `mode`, `delay`,
`bright`, `singleColor` и `modeOptions`. Контроллер допускает только эти поля,
проверяет диапазоны и формат цвета, сохраняет желаемую конфигурацию в
`ws_values`, затем вызывает `WsValues::sendRequest()`. Ошибка доставки возвращает
HTTP 502 с JSON `status=error`: сохранённые параметры не считаются
подтверждёнными устройством.
Результат каждой попытки записывается в `command_delivery`.

Цвета преобразуются из HTML hex в массив чисел и передаются в `ws.lc`. Lua
ограничивает размер буфера, яркость и задержку, запускает выбранный эффект и
сохраняет параметры в `json/ws-action.json`. Старые параметры тестового синего
индикатора игнорируются: WS2812 больше не запускает PWM на D4. Однако сам
WS2812 использует D4 как линию данных, в том числе при выключении ленты.

`ws.lc` принимает только известные режимы и целочисленные диапазоны параметров;
`single_color` должен быть RGB-массивом из трёх чисел `0…255`. Это исключает
перезагрузку обработчика от нечисловых или повреждённых входных значений.
GPIO, PWM и WS записывают состояние через временный файл, сохраняя прежнюю
версию как резервную до успешного переименования. После прерванной записи при
запуске резервный файл используется, если основной отсутствует.
Повтор полностью совпадающего состояния не вызывает повторную запись flash;
PWM и WS также не переинициализируют неизменившийся выход или эффект.

## Периодические команды

- `command/index` обрабатывает только записи `commands` с `pinType=gpio`. Для текущего часа применяются интервалы `[conditionFrom, conditionTo)`, затем состояние отправляется на ESP.
- `dht/index` опрашивает все активные DHT активных устройств.
- `motor/motor` переключает GPIO с `motor=true` по минутному интервалу из настройки `MOTOR_INTERVAL`.

Класс для сохранения расписаний PWM (`CommandsPwmSetSettings`) существует, но метод `set()` не реализован. Исполнитель `CommandController` также не обрабатывает PWM.

## NodeMCU

`nodemcu/code/init.lua`:

1. запускает `compile.lua`;
2. через 100 мс назначает `_G.cjson = sjson`;
3. восстанавливает WS, PWM и GPIO из JSON;
4. настраивает Wi-Fi;
5. запускает TCP HTTP-сервер на порту 80 после получения IP либо сразу в режиме точки доступа.

Обработчики GPIO, PWM и WS загружаются один раз при восстановлении и
переиспользуются HTTP-сервером: их сведения о настроенных выводах и последнем
состоянии сохраняются между запросами.

Кратковременный разрыв Wi-Fi не вызывает `node.restart()` и не переинициализирует
выходы. Пока IP отсутствует, диагностический таймер повторяет проверку каждые
30 секунд; при появлении IP запускает HTTP-сервер один раз.

Исходный `_config.lua` задаёт режим `wifi.SOFTAP`, SSID и пароль `ESP-<chipid>`, адрес `192.168.111.1`. Во время компиляции Lua-файлы превращаются в `.lc`, исходники удаляются из файловой системы ESP.

Единственный поддерживаемый набор Lua-файлов находится в `nodemcu/code/`.

HTTP-сервер NodeMCU принимает только GET и запускает по URL лишь четыре
явно разрешённых модуля: `gpio.lc`, `gpio-pwm.lc`, `dht.lc` и `ws.lc`. Другие
`.lc` и пути с `..` не выдаются. Статические файлы передаются небольшими
порциями по 256 байт после подтверждения предыдущей: чтение целого JS-файла
превышало доступный heap ESP8266 при активном HTTP-соединении.
HTTP-запрос ограничен 2048 байт; сбой обработчика даёт JSON и HTTP 500.
При нехватке свободного heap новый TCP-клиент закрывается без обработки;
это предотвращает перезагрузку ESP при серии частых запросов, клиенту
может потребоваться повторить обращение спустя несколько секунд.
Если в локальной конфигурации задан `conf.general.token`, каждый запрос к ESP
требует заголовок `X-ESP-Token` с тем же значением. Без токена прежний
неаутентифицированный режим остаётся для совместимости.
GPIO, PWM, DHT и WS2812 проверяют владение пином в рамках текущего запуска:
после назначения одного модуля другой не может перенастроить тот же вывод.
Для смены назначения нужен согласованный перенос конфигурации и перезапуск ESP.
Для статичного WS2812-режима ESP загружает компактный эффект; полный каталог
анимаций загружается только при выборе соответствующего режима. Это сохраняет
heap ESP8266 для HTTP-ответа.
