# План развития до production

## Цель

Сделать из текущего приложения надёжную локальную панель управления ESP:
безопасную для физического оборудования, воспроизводимую в развёртывании,
проверяемую без живых устройств и удобную на телефоне.

План эволюционный: сохраняются SQLite-данные, существующие устройства и
рабочие маршруты. Большое переписывание frontend или backend не является
предпосылкой для улучшений.

## Зафиксированный выбор

- Продолжаем Yii2 и server-rendered интерфейс; новый UI строим постепенно на
  шаблонах, CSS-токенах и небольших JS-модулях, а не через немедленный SPA rewrite.
- SQLite сохраняем для текущей небольшой нагрузки. Переход к другой СУБД
  рассматривается только при измеренной потребности.
- Docker Compose — единственный production runtime. Данные остаются в
  persistent-каталогах, не в образе.
- Доступ извне в будущем — через VPN, а не прямое открытие интерфейса или ESP.

## Этапы

### 0. Базовая воспроизводимость

1. Поддерживать документацию, Docker и фактический код согласованными.
2. Настроить isolated SQLite для тестов, migration smoke-test и fake ESP.
3. Добавить CI: Composer validate, PHP lint, тесты, миграции на пустой БД и
   Docker build.
4. Добавить healthcheck, проверяемую SQLite backup/restore и ротацию логов.

**Готово, когда:** изменение можно проверить без действующей БД и ESP, а
развёртывание имеет backup и health gate.

### 1. Безопасный контур управления

1. Ввести пользователей и роли `admin`, `operator`, `viewer`; по умолчанию
   запретить доступ к управляющим действиям.
2. Для интерактивных GPIO, PWM, DHT и WS2812 изменяющие web-endpoint'ы уже
   переведены с GET на POST с CSRF, `VerbFilter`, валидацией и
   структурированным ответом; тот же контракт обязателен для новых действий.
3. Изолировать ESP в доверенной IoT-сети: только сервер имеет доступ к HTTP
   endpoint'ам устройств; у устройств уникальная Wi-Fi-конфигурация.
4. Сделать журнал действий пользователя и audit событий.

**Готово, когда:** случайный клиент локальной сети не может изменить
конфигурацию или физическое состояние устройств.

### 2. Надёжность команд и доменная модель

1. Ввести `DeviceCommandService` и единый ESP transport interface.
2. Хранить желаемое и подтверждённое состояние, время попытки и ошибку доставки.
3. Добавить retry с ограничением, ручной sync устройства и видимый status в UI.
4. Вынести расчёт расписаний в pure service: timezone, минуты, дни недели,
   интервалы через полночь. Motor перевести на state machine с временем
   следующего перехода.
5. После аудита живой БД добавить миграции уникальных индексов, нужных FK и
   индексов истории.

**Готово, когда:** оператор понимает, что команда применена устройством, а
пропуск cron не создаёт непредсказуемого переключения.

### 3. Новый интерфейс

1. Новая оболочка: responsive navigation, design tokens, тёмная тема и
   доступные сенсорные элементы не меньше 44×44 px.
2. Экран «Обзор»: избранные устройства, быстрые действия, датчики, ошибки и
   последние события.
3. Экран устройства: управление, desired/actual status, датчики, история и
   расписания.
4. Технические CRUD-экраны оставить в разделе настроек, не смешивая их с
   повседневным управлением.
5. Добавить browser checks для desktop/mobile и базовую accessibility-проверку.

**Готово, когда:** обычный пользователь может управлять домом с телефона без
понимания пинов, endpoint'ов и технических сущностей.

### 4. Завершение и расширение функций

1. Реализовать или скрыть незавершённые функции: PWM schedules, SSD1306,
   WS-анимации, gamepad.
2. Формализовать и версионировать протокол Yii ↔ ESP; добавить контрактные
   тесты и allowlist обработчиков на ESP.
3. Добавить комнаты, теги и автоматизации по датчикам только после появления
   надёжной модели команд.
4. Планово обновить PHP/Yii/зависимости до поддерживаемой совместимой линии в
   отдельной серии изменений.

## Порядок ближайшей работы

Первый вертикальный срез: тестовый SQLite + fake ESP → безопасный POST API для
GPIO → `DeviceCommandService` с журналом доставки → новая карточка GPIO на
экране «Обзор». Он одновременно укрепляет безопасность, тестируемость и даёт
видимый результат redesign.

## Организация работы

Перед задачей выбирать владельца из `.agents/roles/`: platform/security,
domain/integration, quality/release или frontend/product. Миграции, layout,
asset bundle и deployment-конфигурация всегда имеют одного владельца; смежные
аудиты и тесты можно выполнять параллельно.
